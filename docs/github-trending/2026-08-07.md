**项目定位**

面向想要为 AI 代理提供持久文件系统与可插拔执行后端的开发者。基于 Durable Object + SQLite 权威状态，通过 workspace.runtime.exec 统一执行入口，支持容器 FUSE、isolate shell、isolate JS 三种后端。能力边界：目前是 PREVIEW ONLY，API 不稳定，不适合生产；不提供 GUI，需要自行编排。

**今天相比上次有什么变化**

今日新进 TOP3，暂无昨日同榜对比

**适合谁关注**

适合构建需要持久化、可回滚文件系统的 AI Agent 应用，尤其适合 Cloudflare Workers/边缘生态开发者；适合作为早期探索和原型验证，愿意接受 API 变动、自己封装稳定层的团队。

**不适合谁关注**

不适合需要生产级稳定 API 和长期兼容性的项目；不适合对数据隔离有严格合规要求、尚未评估沙箱安全边界的场景；当前预览版也不适合没有能力跟读源码和快速迭代的普通用户。

**风险或争议点**

预览版风险：API 不稳定，设计可能大改；虚拟文件系统与网络访问边界需要严格权限控制，恶意代码可能逃逸或滥用网络；多后端行为差异可能带来不一致；Cloudflare 厂商锁定风险；执行沙箱安全需独立审计。

**最佳实践场景**

在 Workers 项目中用 @cloudflare/computer 搭建一个"代理工作区"，将代码生成、文件修改、命令执行都落到虚拟文件系统，并让容器后端运行 untrusted 脚本；每次任务生成快照，便于回滚和审计。

- 评估：观察 API 稳定性、任务成功率、文件系统同步延迟，以及沙箱失败率。
- 退出：若两周内 API 频繁破坏性变更或安全边界不满足要求，则降级为自建沙箱方案。

上次记录为 2026-08-06 第 2 名。 今日新增 1190 星，较昨日 2540 星显著回落，star_today_ratio 从 25.5% 降至 9.59%，但仍属高位；近 30 天 PR 从 112 增至 120，issue 从 35 增至 43，社区活跃度上升；总 star 达 1.24 万；仍无公开 release，API 稳定性风险未解除。

**适合谁关注**

适合需要批量处理 PDF 的 RAG 管道，希望先将文本型 PDF 本地化提取、仅对扫描页调用 OCR 以降低成本；适合用 Rust/Python/Node/WASM 多语言集成的团队；也适合在浏览器端做上传前即时分类提示。

**不适合谁关注**

不适合需要 OCR 识别扫描件内容的场景；不适合金融级复杂版式与嵌套表格高精度还原；不推荐直接解析不受信任 PDF 且无沙箱隔离的生产环境；接口未正式 release，不适合长期兼容性要求极高的核心链路。

**风险或争议点**

解析恶意 PDF 存在安全风险，须在隔离沙箱运行；无正式 release，API 可能不兼容变更；性能基准依赖特定硬件，需自行实测；复杂表格/多栏还原可能失真，合同金融文档应人工复核；OCR 路由依赖分类准确率，混合型 PDF 需抽样验证。

**最佳实践场景**

在文档入库管道中先调用 pdf-inspector 按页分类：文本页原地转 Markdown，扫描页才送 OCR 服务；同时对扫描页做人工抽检，对比路由前后处理成本与准确率，形成可量化的智能分流机制。

**我会怎么试用它**

- 安装：pip install pdf-inspector 或 cargo add pdf-inspector；Node 端使用 npm 包。
- 试跑：拿 100 份混合类型 PDF 跑一遍，对比分类结果与人工标注，统计每页置信度。
- 评估：关注分类准确率、解析耗时、Markdown 表格还原度，以及 OCR 调用成本下降比例。
- 退出：若准确率低于阈值或接口频繁破坏性变更，则回退到全量 OCR 或改用成熟商业方案。
