**项目定位**

面向已有安全团队或 SDL 流程的研发组织：把 Claude Code、Cursor 等编码 Agent 编排为侦察、覆盖驱动狩猎、候选验证、结构化输出、独立复核、目标中立报告六阶段流程，产出 findings.json 与 REPORT.md，并附校验脚本。边界在于它是方法学技能框架而非扫描器，不提供漏洞库、托管扫描或自动定级，效果依赖目标代码可读性与 Agent 能力，误报漏报仍需人工判定。

**为什么值得关注**

日增 3607、占总星 34.13%，是三者中爆发最猛的新项目，总星 1.06 万；4 天前有提交，近 30 天 PR 更新 18、issue 更新 9，open issues 30，MIT 许可，README 达 6,536 字符含安装说明与示例。但暂无公开 release、文档入口不明显，属方法论型技能，热度明显领先于生态沉淀，能否转化为稳定维护仍需跟踪。

**适合谁关注**

适合已有漏洞赏金、SDL 或红队流程，且愿投入人工复核的安全团队与安全研究工程师；也适合想把安全审计步骤固化为可复现 prompt、覆盖台账与产物格式的平台团队，在自有代码库或已获授权的目标上做方法验证。

**不适合谁关注**

不适合把 Agent 输出直接当作漏洞结论的团队，其发现必须人工判定；也不适合无安全人员、无授权测试范围或无代码审计基础的团队，更不适合用它对第三方未授权系统做扫描，或试图用它替代专业 SAST/DAST 工具链。

**风险或争议点**

安全审计涉及授权边界：只能对自有或已获书面授权的目标运行，禁止扫描第三方系统；生成的 confirmed 与 needs_validation 记录必须人工复现，不能作为漏洞定级或对外披露的唯一依据。项目暂无 release、文档入口弱，Cloudflare 官方身份需以组织资料核实；缺少漏洞库与误报基准，存在漏报与重复提交争议。

**最佳实践场景**

在自有仓库上以只读权限运行六阶段审计：先由侦察阶段生成 architecture.md 与 coverage-ledger.json，再让独立 verifier 反证候选，所有 confirmed 交由安全工程师复现；把 findings.json 接入内部漏洞平台做去重归档，多轮运行保持累加，用于跟踪修复后的覆盖变化。

- 试跑：选一个自有中型仓库跑完整六阶段，只启用协议与 Web 类攻击提示，人工复核全部候选，逐条记录误报与漏报原因。
- 评估：指标：可复现确认漏洞数、误报率、每轮 token 与耗时、覆盖台账缺口数、修复后重跑能否收敛；与现有 SAST 结果做交叉比对。
- 退出：若连续两轮无可复现确认发现、误报率高于人工基线，或出现越权访问与范围外扫描行为，暂停使用并回收 Agent 权限。

**适合谁关注**

适合已有 CI 流水线、代码不便外发、希望低成本引入行级 AI 审查的中大型团队，尤其关注空指针、线程安全、XSS、SQL 注入等常见缺陷，并能私有化部署模型端点的组织，可先在小范围 PR 上灰度验证再逐步推广。

**不适合谁关注**

不适合指望 AI 替代人工评审的团队，其召回率偏低；也不适合没有 CI 基础、无法配置模型端点或难以承担 token 成本与调用延迟的小团队，更不适合把自动评论直接当作合并门禁，动态语言与复杂业务逻辑仍需人工兜底。

**风险或争议点**

AI 行级建议可能误判，必须保留人工复核，不得自动合入或作为唯一质量门禁；精确率优先意味着存在漏报。规则集源自阿里内部实践，未必适配所有代码规范；依赖外部 LLM 端点会带来延迟、成本波动与代码外发风险，须做企业合规与私有化部署评估。open issues 已升至 206，需警惕反馈积压影响修复时效。

**最佳实践场景**

**我会怎么试用它**

- 安装：安装 Open Code Review CLI，配置 OpenAI 或 Anthropic 兼容的企业内网模型端点与密钥，选 1-2 个语言单一的仓库做只读试跑。
- 试跑：对 20-30 个历史 PR 回放，只对改动行生成评论、默认非阻断，与当时的人工评审意见逐条比对。
- 评估：指标：精确率、召回率、无效评论数、token 消耗与评论延迟、reviewer 采纳率；与通用 Agent 基线对比。
- 退出：若精确率明显低于人工基线、成本或延迟不可接受，或出现代码外发合规风险，即下线并仅保留离线 ocr scan 审计模式。

**适合谁关注**
