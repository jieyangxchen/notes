**项目定位**

面向使用 Claude Code 等 AI 工具处理大型代码库的团队，通过 Tree-sitter 构建结构图谱并提供变更影响范围，减少不必要的 token 消耗；能力边界受语言解析器覆盖度限制，部分语言仅提供基础支持。

**为什么值得关注**

今日 663 星，热度翻倍（日增 355→663）；MIT 许可，维护活跃（2 天前提交，v2.3.7），社区 PR 增至 159，README 内含 benchmark 数据，直击大型仓库的审查效率痛点。

**今天相比上次有什么变化**

上次记录为 2026-07-19 第 3 名。 热度显著上升（355→663 星），社区贡献微增，核心功能稳定在 v2.3.7，未引入大版本变动；提交仍保持 2 天一更的节奏，问题响应及时。

**适合谁关注**

适合有 500+ 文件的 Python / TypeScript / JavaScript 等项目，频繁使用 AI 进行代码审查或重构的团队；注重隐私，所有分析本地运行；可结合 CI 集成。

**不适合谁关注**

不适合小于 100 个文件的小项目，图谱构建开销大于收益；若团队未使用 MCP 兼容工具，集成成本高；语言支持有限，复杂语法（如宏）可能解析错误。

**风险或争议点**

新增工具增加学习成本与维护负担；大型 monorepo 初次构建可能较慢；Tree-sitter 解析误差可能影响上下文准确性，导致 AI 忽略关键变更。

**最佳实践场景**

在拥有 500+ 文件的 Python monorepo 中，集成 code-review-graph 到 Claude Code，发起代码审查，观察其仅读取变更文件及调用链，验证审查速度与全面性提升。

**我会怎么试用它**

- 安装：pip install code-review-graph 或通过 uv 安装，然后在 Git 仓库根目录运行 crg install。
- 试跑：选择一个 >200 文件的中型 Python 项目，执行 crg analyze 生成图谱，然后在 AI 助手内请求一次代码审查。
- 评估：对比使用前后 AI 读取的文件数量、token 消耗及发现的问题数，要求文件数减少 >70%，并确保无关键 bug 遗漏。
- 退出：若连续三次代码审查任务中上下文减少不明显或 AI 遗漏关键 bug，则回归传统方式；若项目变更为小型库则移除。
